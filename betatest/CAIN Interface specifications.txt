CAIN Interface Pack Specification v1.0
=====================================

Status: Frozen v1.0 after approved minor amendments
Scope: CAIN OS / betatest terminal interface system
Last updated: 2026-07-02

1. Purpose
----------

CAIN is being treated as an operating-system-style interface layer, not merely a themed webpage. The terminal is the first application running inside CAIN OS. Interface Packs allow CAIN to change its visual and sensory presentation without changing core behavior, archive logic, navigation, or application state.

An Interface Pack is a presentation package. It may define how CAIN looks, sounds, animates, and feels. It must not define what CAIN does.

Core principle:

    The engine owns behavior.
    The Interface Pack owns presentation.

2. CAIN OS Mental Model
-----------------------

CAIN OS may include these engine-owned subsystems:

- Boot Manager
- Screen / Window Manager
- Input Manager
- Focus Manager
- Audio Manager
- Layout Engine
- Theme Manager
- Asset Registry
- Interface Pack Manager
- Settings Application
- Archive Application
- System Information
- Future applications such as timeline, map, relationship viewer, AI console, exhibit mode, or kiosk mode

Interface Packs sit underneath those systems as presentation resources. They can style and skin the experience, but they do not replace system logic.

3. Terminology
--------------

CAIN OS
    The core application framework. Owns boot flow, navigation, archive loading, input handling, settings, and screen state.

Terminal
    The first CAIN OS application. It currently provides boot, home, archive index, record dossier, and settings screens.

Interface Pack
    A named, self-contained presentation package containing metadata, CSS, fonts, icons, audio, wallpapers, boot imagery, and other static assets.

Pack Loader
    The CAIN OS subsystem that reads the manifest, validates packs, applies the selected pack, and persists user selection.

Layout Engine
    The CAIN OS subsystem that renders engine-defined layouts requested by applications and Interface Packs. The Layout Engine owns structure; Interface Packs only style supported layout profiles.

Theme Manager
    The CAIN OS subsystem that applies, removes, reloads, and reports the active Interface Pack. Application code should use the Theme Manager rather than directly manipulating stylesheet links.

Asset Registry
    The CAIN OS subsystem that resolves named assets from the active Interface Pack. Application code should request assets by semantic key, such as `bootLogo`, `wallpaper`, or `cursor`, rather than reaching directly into pack file paths.

Layout Profile
    An engine-defined layout mode requested by a pack. The pack may request a supported layout, but the engine renders the HTML and controls behavior.

Animation Profile
    An engine-defined animation mode requested by a pack. The pack may request a supported animation profile and provide presentation assets, but CAIN OS owns animation behavior, timing, triggers, and state changes.

Sound Profile
    A set of named audio slots supplied by a pack and triggered by the engine.

4. Non-Negotiable Rules
-----------------------

Interface Packs are presentation-only.

An Interface Pack must never include or require:

- JavaScript
- HTML templates
- inline script
- fetch() calls
- network requests
- third-party runtime dependencies
- behavior overrides
- changes to archive discovery logic
- changes to record parsing logic
- changes to navigation behavior
- changes to settings behavior

Packs may only provide static presentation assets and metadata.

If a future version allows richer pack behavior, that must be introduced through a new specification version and a deliberate CAIN OS compatibility contract. It is prohibited in v1.0.

6. manifest.json
----------------

The manifest is the discovery file for available Interface Packs.

Required file:

    interface-packs/manifest.json

Format:

{
  "spec": "1.0",
  "packs": [
    "phosphor",
    "cadenza-modern",
    "anime-broadcast"
  ]
}

Rules:

- `spec` must match the Interface Pack manifest spec version.
- `packs` is an ordered array of folder names.
- The first valid pack may be used as fallback if no saved preference exists.
- The loader should skip invalid or incompatible packs and continue loading the rest.
- The Settings Application should present packs in manifest order unless a future sorting rule is defined.

Rationale:

Named folders plus a manifest make Interface Packs readable and product-like. Archive records use numbered folders because they are chronological records. Interface Packs are named interface products and should remain human-readable.

------------

Every Interface Pack must include:

    pack.json

Required fields:

  "id": "phosphor",
  "uuid": "4f89d98d-a3fe-49d5-b1bc-000000000001",
  "name": "Green Phosphor",
  "description": "Classic green CRT terminal interface for CAIN OS.",
  "author": "Cadenza Arthouse",
  "spec": "1.0",
  "packVersion": "1.0.0",
  "minimumOS": "1.0.0",
  "maximumOS": "1.x",
  "layout": "terminal-classic",
  "animationProfile": "crt-flicker",
  "soundProfile": "terminal-basic",
  "entry": {
    "css": "skin.css"
  },
  "assets": {
    "preview": "preview.png",
    "bootLogo": "boot/logo.png",
    "wallpaper": "wallpapers/default.png",
    "cursor": "icons/cursor.png"
  },
  "sounds": {
    "boot": "sounds/boot.wav",

    "back": "sounds/back.wav",
    "error": "sounds/error.wav",
    "confirm": "sounds/confirm.wav"

    "audio": true,

  "certification": "official"

8. pack.json Field Rules
------------------------

id
    Required. Must match the pack folder name. Lowercase kebab-case only.

uuid
    Required. Permanent unique pack identifier. Must be a UUID string. The UUID is the stable identity used for long-term compatibility, migration, and saved preferences. Folder names and human-readable IDs may change; UUIDs should not.

name
    Required. Human-friendly display name shown in settings.

description
    Required. One or two sentence summary of the pack.

author
    Required. Creator or organization name.

spec
    Required. Interface Pack Specification version. Initial value: "1.0".

packVersion
    Required. Semantic pack version. Example: "1.0.0".

minimumOS
    Required. Minimum CAIN OS version supported by the pack.

maximumOS
    Required. Maximum CAIN OS version or compatibility family. Example: "1.x".

layout
    Required. Must be one of the engine-supported layout profiles.

animationProfile
    Required. Must be one of the engine-supported animation profiles.

soundProfile
    Required if audio is supported. Must be one of the engine-supported sound profile categories.

entry.css
    Required. Relative path to the pack's main CSS file.

assets.preview
    Required. Relative path to a preview image used in settings.

assets.bootLogo
    Optional. Relative path to boot logo or mark.

assets.wallpaper
    Optional. Relative path to pack wallpaper/background.

assets.cursor
    Optional. Relative path to cursor image.

sounds
    Optional if `supports.audio` is false. Required slots may be filled by fallback engine sounds if missing.

supports
    Required. Capability flags used by the engine to decide which effects and controls to enable.

certification
    Optional. Suggested values: "official", "community", "experimental".

9. Layout Engine and Supported Layout Profiles v1.0
---------------------------------------------------

The Layout Engine owns all layout profiles. Interface Packs may request one.

CAIN OS should call the Layout Engine to render known layouts, then apply the selected Interface Pack through the Theme Manager.

Conceptual flow:

    LayoutEngine.load("terminal-classic")
    ThemeManager.applyTheme("phosphor")

This keeps layouts reusable across packs. For example, `terminal-classic` may be styled as green CRT, amber CRT, DOS, IBM, or blue LCD without changing layout behavior. Likewise, `broadcast` may be styled as anime, cartoon, or music-television inspired without each pack defining its own HTML.

Initial supported layout profiles:

terminal-classic
    Current CAIN terminal structure: boot screen, side menu, archive index, dossier reader.

modern-panels
    Higher-color interface using panels, status surfaces, and more contemporary dashboard spacing.

broadcast
    High-energy display mode suitable for anime, television, 1990s cartoon, or media-console styling.

accessibility
    Large type, higher contrast, reduced visual noise, strong focus states.

Rules:

- Packs cannot define arbitrary layouts.
- Packs cannot provide HTML templates.
- Packs request layout profiles; CAIN OS decides how those layouts render.
- Unsupported layout requests fall back to `terminal-classic`.
- Layout additions require updating this specification or a future spec version.

10. Supported Animation Profiles v1.0
-------------------------------------

Animation behavior belongs to CAIN OS. Interface Packs do not own animation behavior, timing, or triggers.

An Interface Pack may request an animation profile and provide presentation values or assets used by that profile. The engine remains responsible for opening windows, switching screens, changing focus, and coordinating transitions.

Conceptual flow:

    AnimationManager.use("crt-flicker")
    ThemeManager.applyTheme("phosphor")

The pack may supply colors, glow levels, opacity variables, scanline textures, or CSS classes. It must not implement application state transitions or custom interaction behavior.

Initial supported animation profiles:

none
    No motion beyond required state changes.

instant
    Immediate transitions.

fade
    Simple opacity transitions.

crt-flicker
    Subtle CRT flicker, scanlines, and glow transitions.

slide
    Directional panel transitions.

pixel-pop
    Snappy pixel/broadcast-style appearance transitions.

Rules:

- Animation behavior is implemented by CAIN OS.
- Packs only request a profile and style supporting CSS variables/classes.
- Packs must not define behavior-dependent animation logic.
- Packs must not use animation to hide or bypass required navigation, focus, or record-reading states.
- User accessibility preferences should override pack animation when necessary.

11. Sound Profile v1.0
----------------------

The engine triggers named sound events. Packs provide files for those events.

Standard sound slots:

- boot
- hover
- select
- back
- error
- confirm
- open
- close

Rules:

- Sounds are optional only when `supports.audio` is false.
- Missing sound files should fall back to generated Web Audio or silence.
- Packs must not execute code to play sounds.
- CAIN OS decides when to play sounds.

12. CSS Contract
----------------

Each pack must include a CSS file defined by `entry.css`.

Required file:

    skin.css

The CSS may:

- Set CSS custom properties.
- Style documented CAIN OS classes and data attributes.
- Use pack-local fonts and images.
- Define presentation-only animations.
- Style supported layout profiles.

The CSS must not:

- Hide critical navigation permanently.
- Break focus visibility.
- Prevent reading archive records.
- Rely on remote assets.
- Import remote CSS.
- Use behavior-dependent hacks that require custom JavaScript.

Initial core variables:

--bg-color
--text-color
--text-glow
--panel-border
--font-main
--font-heading
--accent-color
--surface-color
--muted-text-color
--focus-color
--danger-color
--success-color
--wallpaper-image
--scanline-opacity
--crt-vignette-opacity

13. Asset Path Rules
--------------------

All asset paths in `pack.json` are relative to the pack folder.

Example:

    interface-packs/phosphor/pack.json
    interface-packs/phosphor/skin.css
    interface-packs/phosphor/assets/frame.png

A pack may reference its own assets from CSS using relative URLs.

Example:

    background-image: url("assets/frame.png");

Rules:

- No remote asset URLs.
- No absolute URLs unless explicitly approved in a future spec.
- Assets should be optimized for web delivery.
- Preview images should be lightweight.

14. Theme Manager Contract
--------------------------

The Theme Manager is the only CAIN OS subsystem that should apply or remove Interface Pack presentation at runtime.

Required responsibilities:

- Track the active Interface Pack.
- Apply the active pack CSS.
- Remove or replace previously applied pack CSS.
- Apply body-level pack classes and layout classes.
- Persist valid user selections through the Settings Application.
- Fall back safely when a saved pack is missing, invalid, or incompatible.

Minimum conceptual API:

    ThemeManager.applyTheme(packIdOrUuid)
    ThemeManager.removeTheme()
    ThemeManager.currentTheme()
    ThemeManager.reloadTheme()

Rules:

- Screens and applications should not directly manipulate Interface Pack stylesheet links.
- Screens and applications should ask the Theme Manager for current pack metadata when needed.
- Theme Manager behavior belongs to CAIN OS, not to packs.

15. Asset Registry Contract
---------------------------

The Asset Registry resolves named assets from the active Interface Pack.

Application code should request assets by semantic name:

    Assets.get("bootLogo")
    Assets.get("wallpaper")
    Assets.get("cursor")
    Assets.get("preview")

The application should not hardcode pack-relative paths such as:

    interface-packs/phosphor/boot/logo.png

Required responsibilities:

- Resolve pack-relative asset paths.
- Provide fallback assets when a pack omits optional assets.
- Prevent remote or invalid asset URLs.
- Expose semantic asset keys to boot, settings, layout, and display systems.

Initial asset keys:

- preview
- bootLogo
- wallpaper
- cursor
- iconSet
- windowFrame
- panelTexture
- scanlineTexture

Rules:

- Asset Registry behavior belongs to CAIN OS.
- Packs declare assets; they do not load assets through JavaScript.
- Missing optional assets must not crash CAIN OS.

16. Compatibility and Versioning
--------------------------------

CAIN OS must define its current OS version.

Example:

    CAIN OS 1.0.0

Each pack declares:

- `uuid`
- `spec`
- `packVersion`
- `minimumOS`
- `maximumOS`

Loader behavior:

- If `spec` is unsupported, skip the pack.
- If `uuid` is missing or malformed, the pack is invalid.
- If current CAIN OS is below `minimumOS`, skip the pack.
- If current CAIN OS exceeds `maximumOS`, warn or skip depending on strictness.
- If `packVersion` is malformed, the pack is invalid.

This prevents older packs from failing mysteriously as CAIN OS evolves.

17. Capability Flags
--------------------

Capability flags tell the engine what the pack supports.

Initial flags:

animations
wallpaper
crt
audio
scanlines
customCursor
highColor
reducedMotion
largeType

Rules:

- Missing flags should be treated as false.
- A pack should not request effects it does not support.
- The Settings Application may use flags to label packs for users.

18. Certification
-----------------

Certification is optional in v1.0 but reserved for future use.

Suggested values:

- official
- community
- experimental

Settings may eventually display certification labels.

Example:

    Official Cadenza Interface
    Community Interface
    Experimental Interface

19. Required Pack Documentation
-------------------------------

Each contributed Interface Pack should include:

README.md
    Describes the concept, supported layout, credits, and usage notes.

LICENSE
    Defines licensing for pack assets.

CHANGELOG.md
    Tracks pack changes over time.

These files are recommended for v1.0 and may become required for community contribution workflows later.

20. Discovery and Loading Flow
------------------------------

CAIN OS Interface Pack Loader should:

1. Fetch `interface-packs/manifest.json`.
2. Validate the manifest spec.
3. Read pack folder names in order.
4. Fetch each `pack.json`.
5. Validate required fields.
6. Check spec and OS compatibility.
7. Register valid packs.
8. Load the saved pack from localStorage if valid.
9. Otherwise load the default pack.
10. Ask the Layout Engine to load the selected layout profile.
11. Ask the Theme Manager to apply the selected pack.
12. Register pack assets with the Asset Registry.
13. Expose available packs to the Display Settings screen.

21. User Selection and Persistence
----------------------------------

The selected Interface Pack should be stored in localStorage.

Suggested key:

    cain.interfacePack

The stored value should prefer the pack UUID. The pack ID may be stored as a secondary convenience value for debugging and readability.

If the stored pack is missing, invalid, or incompatible, CAIN OS should fall back to the first valid pack in the manifest.

22. Display Settings Application
--------------------------------

The Settings Application should allow users to:

- View available Interface Packs.
- See name, description, preview, author, version, UUID, compatibility, and certification.
- Switch packs.
- Persist their selection.
- Return to the main menu.

Future settings may include:

- Reduced motion override
- Audio on/off
- Large type override
- High contrast override
- Reset to default interface

23. Default Packs for First Implementation
------------------------------------------

The first implementation should prove that the architecture supports radically different presentation without changing CAIN OS behavior.

Recommended initial packs:

phosphor
    Current green CRT terminal look. This should be the default and compatibility baseline.

cadenza-modern
    High-color modern archive workstation. More polished, editorial, and contemporary.

anime-broadcast or cartoon90
    A visually extreme pack proving that CAIN can support a very different interface identity through the same engine.

24. First Implementation Milestone
----------------------------------

The Interface Pack system must support the Archive terminal, not replace the project focus.

The first implementation should prove one complete vertical slice:

1. Boot CAIN.
2. Enter the home screen.
3. Open the archive.
4. Browse records.
5. Open and read a record dossier.
6. Open Display Settings.
7. Switch to the Green Phosphor Interface Pack.
8. Confirm archive navigation and record reading continue to work.

Initial build scope:

- Pack Loader
- Theme Manager
- Asset Registry
- Layout Engine integration for existing terminal layouts
- Green Phosphor Interface Pack
- Display Settings screen

The first build should validate the architecture with working software. Future revisions should follow:

    Freeze -> Build -> Learn -> Revise

Not:

    Design -> Design -> Design -> Design

After this v1.0 specification is frozen, implementation experience should drive future v1.1 changes.

25. Contributor Workflow
------------------------

A contributor creating a new Interface Pack should:

1. Read `interface-packs/README.md`.
2. Create a named folder under `interface-packs/`.
3. Add `pack.json`.
4. Add `skin.css`.
5. Add `preview.png`.
6. Add optional assets, sounds, fonts, icons, boot art, and wallpapers.
7. Add README, LICENSE, and CHANGELOG when applicable.
8. Add the folder name to `manifest.json`.
9. Test pack loading in the Display Settings screen.
10. Confirm archive navigation and record reading still work.

26. Validation Expectations
---------------------------

The loader should tolerate bad packs gracefully.

If a pack is invalid:

- Do not crash CAIN OS.
- Do not break the active interface.
- Log a warning to the console.
- Skip the pack in Settings.

If the active saved pack becomes invalid:

- Fall back to the default valid pack.
- Update localStorage to the fallback pack.

28. Summary Contract
--------------------

CAIN OS is the engine.
Interface Packs are presentation packages.
The engine controls behavior.
Packs control look, sound, motion profile, and static assets.
The Layout Engine owns structure.
The Theme Manager owns theme application.
The Asset Registry owns semantic asset resolution.
No pack JavaScript.
No pack HTML.
No pack network access.
All behavior changes must happen in CAIN OS, not in packs.

This specification is frozen as v1.0. It is the contract for building the first Interface Pack loader, Theme Manager, Asset Registry, Layout Engine integration, Green Phosphor Interface Pack, and Display Settings screen.
